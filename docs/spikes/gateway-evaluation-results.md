# Gateway evaluation results

## Status

Slice 0.2 measured result and proposed recommendation. The recommendation is **not accepted architecture** until the maintainer approves it. No gateway ADR has been created.

Evaluation date: 2026-07-25.

The test and scoring rules are defined in the [gateway evaluation contract](gateway-evaluation.md). The tracked comparison harness is under [`../../spikes/gateway-evaluation/`](../../spikes/gateway-evaluation/README.md). It is evidence code, not a production package.

## Proposed recommendation

Build the shared project gateway as an LCTK-owned Go component inside the single `lctk` executable. Keep the host registry authoritative, expose `/projects/{project_id}/mcp`, validate the route and project grant before dispatch, and proxy to the project-local aggregated MCP service. Do not adopt ContextForge, Docker MCP Gateway, or MCPJungle as an additional production control plane for the first product architecture.

This recommendation is based on boundary fit rather than benchmark rank alone:

- LCTK already owns the host registry, secrets, project lifecycle, health model, and stable public MCP contract.
- The gateway's differentiating responsibility is route-bound project scope and typed lifecycle failure, not third-party server catalog management.
- The custom proof is the only candidate that directly matched LCTK's required public route, grant, typed-error contract, and single authoritative registry without an adapter or second control plane.
- MCPJungle is the strongest external alternative, but adopting it would retain a second registry and administration model while LCTK still owns the public router, lifecycle translation, and stable aggregate tools.
- ContextForge also proved native virtual-server route/grant binding with server-scoped JWTs, but its generated route identifiers, operational footprint, and broader administration model still require a substantial LCTK adapter.
- The production implementation should reuse the verified contract and tests, not promote the proof harness unchanged. Persistent records, grants, key handling, lifecycle reconciliation, observability, and migrations remain host-daemon responsibilities.

MCPJungle and ContextForge can be placed behind a path and error façade. ## Protocol and resource measurements

### Readiness and footprint

| Candidate | Ready time | Configured idle memory | Image size | Socket or project mounts |
|---|---:|---:|---:|---|
| Custom Go | 324 ms | 6.74 MiB | 3,503,972 bytes | None |
| MCPJungle enterprise | 196 ms initial; 49 ms restart | 13.66 MiB | 23,156,272 bytes | None |
| ContextForge, one worker | 16.8-21.0 s | 424-456 MiB | 128,212,259 bytes | None |
| Docker MCP Gateway | 268 ms | 13.78 MiB | 40,229,970 bytes | None in the final static validation; benchmark run mounted the socket read-write |

ContextForge's default automatic worker count consumed approximately 2.73 GiB on this host. The measured configuration constrained it to one Gunicorn worker. It also required explicit JWT issuer/audience/secret settings, platform administrator setup, private-network SSRF allowance for the isolated Docker network, and several auxiliary secret/password settings to eliminate startup warnings.

Docker MCP Gateway failed twice without the socket in its default non-static mode: first while guessing the Docker network and then while pinging the daemon. The benchmark run therefore mounted `/var/run/docker.sock` read-write. Source review then showed that `--static` skips image verification and in-container network discovery. A controlled rerun of the pinned image with the same remote-only catalog, `--static`, and no socket initialized in 17.64 ms according to its log, listed all four tools, and passed the official-client probe. Container inspection confirmed that its only bind mount was the read-only catalog; an anonymous `/misc` volume was also created. The no-socket hard gate therefore passes only for the static remote-server configuration.

### Warm `tools/call`

One warm-up call preceded 100 sequential `project_info` calls.

| Candidate | Success | Median | p95 | Mean | Reconnect |
|---|---:|---:|---:|---:|---|
| Custom Go | 100/100 | 1.590 ms | 2.229 ms | 1.688 ms | Pass |
| MCPJungle enterprise | 100/100 | 4.804 ms | 6.026 ms | 4.835 ms | Pass |
| ContextForge | 100/100 | 42.606 ms | 73.174 ms | 47.604 ms | Pass |
| Docker MCP Gateway | 100/100 | 2.139 ms | 3.022 ms | 2.228 ms | Pass |

ContextForge's default medium-tier rate limit is 100 requests per minute and caused the first 100-call attempt to be throttled after setup traffic. The reported 100/100 run used `RATE_LIMITING_ENABLED=false` in a disposable snapshot of the configured candidate. This isolates forwarding latency but also records rate-limit tuning as required deployment configuration.

### Dynamic lifecycle

| Candidate | Registration/change evidence | Removal evidence |
|---|---|---|
| Custom Go | Live gamma route: 34.96 ms, immediately callable | 6.20 ms; route then returned `PROJECT_NOT_FOUND` |
| MCPJungle | Server registration 154-156 ms plus group creation 126-135 ms | Group deletion 141 ms plus server deregistration 151 ms |
| ContextForge | Gateway registration 46-140 ms plus virtual-server creation 26-84 ms | Virtual-server deletion 83 ms plus gateway deletion 35 ms |
| Docker MCP Gateway | Static catalog in the measured run; both projects appeared on one endpoint | Not applicable to a project route |

MCPJungle enterprise state, groups, and client grants survived a container restart. ContextForge gateway and virtual-server records also persisted. The custom proof deliberately keeps records in memory because the proposed production gateway is part of `lctk` and is hydrated from the daemon-owned persistent registry; it must not create a second authoritative database.

## Scope and grant observations

### Custom Go

- `/projects/alpha/mcp` listed only `alpha_only` and `project_info`.
- `/projects/beta/mcp` listed only `beta_only` and `project_info`.
- Spoofed `project_id`, `repository_root`, and traversal-like `path` arguments did not change the upstream's immutable project identity.
- An alpha grant on the beta route returned HTTP 403 before MCP dispatch.
- External project grants were stripped before forwarding to the internal project service.

### MCPJungle

- `/v0/groups/alpha/mcp` and `/v0/groups/beta/mcp` listed only their assigned tools.
- Enterprise client allowlists enforced server access. An alpha-only token on the beta group initialized but received an empty tool list; it did not receive a stable authorization failure.
- Development mode accepted the same arbitrary bearer value on either group and therefore cannot provide downstream grant enforcement.
- Group endpoints currently expose tools but not prompts or resources, as documented in `docs/limitations.mdx` and the tool-group guide at the pinned source.
- The pinned source contains a TODO in `internal/model/mcp_server.go` to encrypt upstream bearer tokens instead of storing them as plaintext.

### ContextForge

- Separate virtual servers listed only the two tools assigned to alpha or beta.
- Tool names were gateway-prefixed and endpoints used generated server IDs rather than stable project routes.
- The original platform-administrator token could access both routes.
- A second runtime check generated native JWTs with `scopes.server_id`. A beta-scoped token listed and called beta tools successfully, while a token scoped to another server received HTTP 403 during initialization on the beta route. ContextForge therefore enforces the route/grant agreement natively for virtual servers.
- A restart preserved records, but the health endpoint became ready before the virtual MCP route was immediately reliable; a subsequent retry succeeded. LCTK would need a stronger readiness adapter.

### Docker MCP Gateway

- With both upstreams enabled, the only measured route was `/mcp` and it listed all four tools: alpha and beta `project_info` plus both sentinels. The final `--static` no-socket rerun exposed the same combined tool set.
- Duplicate stable names required catalog prefixes.
- Separate project routes and independent route grants would require one gateway process per project or an authoritative LCTK router in front. The latter is already the custom gateway boundary.

## Failure behavior

| Candidate | Upstream unavailable result |
|---|---|
| Custom Go | HTTP 503 with `SERVICE_UNAVAILABLE`, `retryable: true`, project ID, and request ID |
| MCPJungle | Failure after about 1.88 s with raw DNS/transport details in MCP error text |
| ContextForge | Failure after about 2.02 s with low-level name-resolution text |
| Docker MCP Gateway | Failure after about 3.75 s with raw connection and DNS details |

The custom candidate also returned the provisional typed envelope for:

- HTTP 404 `PROJECT_NOT_FOUND`;
- HTTP 401 `AUTH_REQUIRED`;
- HTTP 403 `AUTH_FORBIDDEN`;
- HTTP 503 `SERVICE_UNAVAILABLE`.

No external candidate natively matched the provisional LCTK failure envelope. ContextForge and MCPJungle provide useful administration errors, but their MCP forwarding failures would still require translation at LCTK's public boundary.

## Weighted score

Scores use the contract's five-point scale. A high score does not override a failed hard gate.

| Criterion | Weight | Custom Go | MCPJungle | ContextForge | Docker MCP Gateway |
|---|---:|---:|---:|---:|---:|
| Project scope and authorization | 30 | 5 | 4 | 4 | 1 |
| MCP behavior and reconnect | 20 | 5 | 5 | 4 | 4 |
| Dynamic lifecycle and configuration | 15 | 5 | 4 | 4 | 2 |
| Operational simplicity and overhead | 15 | 5 | 5 | 1 | 3 |
| Stable API fit and adapter size | 10 | 4 | 2 | 2 | 1 |
| Maintenance, release, and license posture | 10 | 3 | 4 | 4 | 4 |
| **Weighted total / 100** |  | **94** | **83** | **67** | **47** |

Score rationale:

- **Custom Go:** direct contract fit and lowest overhead; loses maintenance points because LCTK owns the gateway implementation and protocol tests. The tracked evidence is 489 source lines and 158 test lines, including upstreams, client probes, benchmark code, and the proof gateway.
- **MCPJungle:** reliable and lightweight with useful enterprise allowlists and dynamic groups; loses API-fit points for the group route, untyped failures, tool renaming, tool-only groups, and duplicated control state.
- **ContextForge:** broad and capable, with dynamic virtual servers and verified server-scoped JWT enforcement; loses operational and API-fit points because its footprint, setup, generated route identifiers, tool naming, readiness, and administration model substantially exceed LCTK's gateway boundary.
- **Docker MCP Gateway:** static mode removes the Docker-socket objection for remote-only catalogs, but good forwarding latency and active maintenance do not compensate for the shared route and lack of project-grant semantics.

## Decision boundary

Maintainer approval is required before the following actions:

1. recording an ADR that selects the LCTK-owned Go gateway;
2. implementing the production gateway in `internal/`;
3. treating the proposed route, grant, and failure envelope as accepted public contracts.

If approved, the next implementation step is not to import the spike package. It is to define production interfaces around the daemon registry, grant validator, project health resolver, and MCP upstream transport, then deliver Slice 1.3 through tested vertical behavior.
